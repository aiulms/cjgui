# 代码质量与交付判断

更新：2026-09-11。操作与验证规则统一在 [AGENTS.md](../../AGENTS.md)，例外解释见 [治理总则](../core/GUI_GOVERNANCE.md)。

审阅代码时围绕四件事：

1. 用户和应用开发者获得了什么真实能力，正常消费入口在哪里。
2. 状态修改是否有明确业务归属，人的入口与外部入口是否调用同一实际操作。
3. 失败、版本冲突、权限与资源生命周期是否正确处理。
4. 已有检查是否覆盖实际改动，运行与发布结论是否有证据。

不要以固定代码行数、类型数或拆分文件数判定质量。
大文件或复杂改动应按职责与实际维护风险处理，不默认要求先做全仓重构。
注释默认中文，解释关键约束、生命周期和不明显的选择；无需给每个字段机械填写治理注释。
普通类型/结果结构可以存在；反对的是只改名传递 Bool 摘要、没有真实执行或消费方的重复包装。
测试用于验证行为与失败路径，不用于证明一串自设摘要互相吻合。

文档任务按文档检查，代码任务按改动范围检查。旧 probe/assertion 的成功不能替代当前应用集成。
状态写入要说明前后值与读回；画面显示要有真实窗口证据；外部调用要说明是否实际模型执行。
API 标为 experimental 时应有真实消费样例；不可因“还不稳定”永远隐藏到临时同 package 探针。

报告只需实际变化、证据、风险与缺口。无需补齐旧版五道门和逐项封账表。
