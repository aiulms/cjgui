# 仓颉 GUI 框架项目方向

最后更新：2026-04-25

性质：project-direction / architecture-brief / intent record
状态：生效中
范围：用于向架构管理 AI、执行 AI、未来维护者说明本项目的动机、审美、方向和边界

## 0. 一句话方向

我们想做的是：

> 一个用仓颉语言构建的、核心由自己掌控的、走自绘和 GPU 加速路线的、极致轻量的通用 GUI 框架。

它不是 Electron 式应用壳，不是 Qt 绑定，不是 WebView 包装。
它更接近“用仓颉重新表达 GPUI / WGPUI 一类框架的骨架思想”。

## 1. 对现有 GUI 框架的态度

| 框架 | 态度 | 原因 |
| --- | --- | --- |
| Electron | 强烈不选 | 运行时臃肿，每个应用都像带着一个独立浏览器 |
| Qt | 尊重但不选为主线 | 能力强，但太重，C++ 依赖和历史包袱都不符合本项目初心 |
| Flutter | 认可其野心 | 自绘引擎、垂直深度和主权思想值得学习 |
| GPUI | 重点参考 | GPU 加速、自绘路线、Entity 驱动思想和高性能目标值得认真研究 |
| WGPUI | 最直接参照 | 更接近我们想研究的通用 GUI 框架骨架 |
| Tauri | 部分认可 | 轻量化方向值得尊重，但 WebView 渲染路线不是本项目主线 |

## 2. 我们想做的框架

关键特征：

- 主权在我：不基于 Rust 生态，不绑定外部重型 GUI 框架，核心框架层尽量由仓颉实现。
- 极致性能：参考 GPUI 的 GPU 加速和高刷新率目标，但第一阶段先验证最小绘制链路。
- 极轻体重：框架服务应用，而不是让应用背着巨大运行时。
- 通用性：目标是服务仓颉桌面应用开发者，而不是只服务某一个具体产品。
- AI-readable / Agent-operable：长期目标不是内置 AI，而是让 UI 能从同一份状态真相投影出像素和语义。
- 教学级架构：每一层都应该能讲清楚，个人开发者能从头理解到尾。

## 3. 核心参照系

| 框架 | 参考深度 | 具体参考内容 |
| --- | --- | --- |
| WGPUI | 骨架级 | Entity / Context 思想、组件组织、GPU 渲染管线、通用框架表达 |
| GPUI | 哲学级 | 性能标杆、GPU 直绘勇气、状态与渲染分离方式 |
| Flutter | 架构级 | 自绘主权思想、分层架构、平台嵌入层和框架层分离 |
| Qt | 策略级 | 输入法、无障碍、系统主题、平台复杂性的长期处理经验 |

## 4. 当前技术路线倾向

当前方向倾向如下：

- 用仓颉从零表达框架骨架，而不是做 WGPUI 或 GPUI 的仓颉绑定。
- 走自绘路线，不走原生控件薄绑定，不走 WebView 主路线。
- 第一阶段优先考虑 macOS 单平台。
- 第一阶段优先验证窗口、事件循环、基础 GPU 绘制和画矩形。
- 第一阶段不做跨平台、不做输入框、不做 IME、不做无障碍、不做 DSL、不做完整控件库。

注意：

- `macOS + Metal` 是当前强倾向，不是已经通过 preflight 冻结的最终结论。
- `120fps` 是长期性能愿景，不是 P0 的验收标准。
- “核心 100% 仓颉”指框架主体逻辑，不否认底层必须有平台桥接。
- 平台桥接更准确的目标是“向上接口极窄”，而不是代码量越薄越好；macOS 脏活可以留在平台层消化，但不能泄露成公共契约。

## 5. 个人动机

这个项目不是单纯为了交付一个商业工具。

更深的动机是：

- 为爱发电。
- 给仓颉生态补一块缺失的 GUI 基础设施。
- 做一个垂直深度足够强的底座，而不是只堆功能广度。
- 验证一套轻量治理框架能否驾驭复杂系统。
- 让未来自己用仓颉开发桌面应用时有一条真正属于仓颉的路。

## 6. 必须遵守的约束

1. 框架核心尽量由仓颉实现，底层只允许必要且向上接口极窄的平台桥接。
2. 不依赖 Electron、Qt、GTK、Flutter 这类重型 GUI 框架作为主路线。
3. 不基于 Rust 生态作为核心运行时。
4. 公共 API 只能投影底层真实能力，不能为了 demo 好看而发明。
5. 渲染永远是状态的投影，渲染结果不能自持 UI 真相。
6. 第一平台跑稳之前，不做跨平台抽象。
7. 输入框、IME、无障碍、复杂文本系统必须后期开口。
8. AI 语义树只能是 UI 状态真相的投影，不能成为第二真相源。
9. 桥接层可以处理平台复杂性，但向上接口必须极窄、标准化、可测试。
10. 快、轻、小、可解释，比大、全、重更优先。

## 7. 给架构管理 AI 的口径

后续架构设计请默认接受以下前提：

- 主线参考 GPUI / WGPUI，而不是 Qt / Electron。
- 目标是用仓颉重新表达这种框架骨架，不是绑定现有框架。
- 第一阶段先证明最小桌面运行时和最小绘制链路。
- P1 桥接边界清理必须优先回答 FFI 生命周期、主线程 owner、错误边界和窄接口问题。
- AI 原生 UI 语义方向只作为长期预留，不允许提前打开 semantic tree / action router 实现。
- 任何高层 API、组件语法、DSL、跨平台抽象，都必须建立在真实底座之后。
- 若技术选型与本方向冲突，必须先开 docs-only approval gate。
