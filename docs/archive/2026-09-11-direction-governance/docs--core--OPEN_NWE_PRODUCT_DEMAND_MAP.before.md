# open-nwe 对仓颉 GUI 的产品需求映射

最后更新：2026-04-25

## 1. 文档定位

本文件不是 `open-nwe` 前端迁移计划。

它只回答一个问题：

> 如果未来希望 `open-nwe` 这样的真实应用使用我们自研的仓颉 GUI 框架，那么这个应用会给 GUI 框架带来哪些长期压力？

当前结论：

- `open-nwe` 的现有 React 前端可以被放弃。
- 现有前端组件、CSS、Tailwind、Monaco、xterm 不是仓颉 GUI 框架的直接蓝本。
- 真正值得参考的是 `open-nwe` 的产品形态、信息密度、长任务交互、治理证据和开发者工具面。
- 本文件只作为 future demand map，不批准任何运行时代码实现。

## 2. open-nwe 的产品本质

按当前仓库现实，`open-nwe` 更像一个 Agent OS / Agent 编排平台，而不是普通聊天应用。

它的核心产品能力包括：

- 长期任务：`Mission / MissionStep / MissionEvent`
- 执行账本：`TaskTicket / execution_jobs`
- 治理与审计：`ExecutionProfile / PolicyDecision / governance action`
- Agent 编排：`AgentLoop / AgentExecutionSupervisor / SkillExecutor`
- 多入口协作：`chat / code-review / workflows / group / Feishu ingress`
- 开发者工具面：代码编辑器、终端、插件商店、模型池、运行状态监控

这意味着它未来需要的不是一个漂亮页面壳，而是一套能承载复杂工作台的桌面 UI 基座。

## 3. 对仓颉 GUI 的长期能力压力

### 3.1 App Shell / 工作台外壳

`open-nwe` 需要多工作区、多功能入口、可长期停留的桌面工作台。

GUI 框架未来会需要：

- 主窗口
- 侧边栏
- 顶部或局部工具栏
- 多面板内容区
- 可折叠导航
- 滚动区域
- 弹层 / 抽屉 / 对话框
- 面板间焦点管理

这类能力不能在第一阶段做，但它说明未来布局系统不能只服务简单 demo。

### 3.2 长列表 / 表格 / 状态面板

Mission、Task、ExecutionJob、Agent、Plugin、ModelPool 都天然是列表或表格型界面。

GUI 框架未来会需要：

- 高效列表
- 行选择
- 状态 badge
- 分组
- 筛选 / 搜索
- 局部刷新
- 空状态 / 错误状态 / loading 状态
- 大量数据下的滚动性能

这会反向要求我们早期不要把布局和绘制写死在单个控件里。

### 3.3 对话与流式内容

`open-nwe` 的 chat 不是简单输入框加结果，而是多目标、多模型、可带附件、可显示 resolved model truth 的工作流入口。

GUI 框架未来会需要：

- 消息流
- 自动滚动
- 长文本换行
- Markdown 或富文本的最小能力
- 流式增量更新
- 输入框
- 附件展示
- 复制、选择、上下文菜单

注意：这会引爆文本系统和输入法系统，不能过早进入实现。

### 3.4 任务运行与审计证据

`open-nwe` 的重要 UI 不只是展示结果，还要展示“为什么是这个状态”。

GUI 框架未来会需要：

- 状态时间线
- 事件流
- 日志视图
- 只读证据面板
- 可展开详情
- 错误和降级状态的诚实表达

这对 GUI 的要求不是“好看”，而是要能稳定表达复杂状态和证据链。

### 3.5 开发者工具面

`open-nwe` 当前已有代码编辑器和终端能力。即使现有前端可放弃，这类产品能力仍可能保留。

GUI 框架未来会需要：

- 等宽字体文本显示
- 大文本滚动
- 光标 / 选择 / 输入
- 终端式字符网格
- 代码编辑器级别的文本能力
- 快捷键
- 文件树

这部分属于后期硬仗，不应成为早期目标。

### 3.6 主题与信息密度

`open-nwe` 是高信息密度工具，不是营销页。

GUI 框架未来会需要：

- 主题 token
- 颜色语义
- 状态语义色
- 深色 / 浅色
- 字体和间距系统
- 高密度布局
- 可读性和对比度治理

早期不需要做主题系统，但渲染命令和控件属性不能把颜色、尺寸、状态写死到不可替换。

## 4. 对当前仓颉 GUI 路线的约束

`open-nwe` 可以作为北极星，但不能作为第一阶段宿主。

当前必须守住：

- 不把 `open-nwe` 当前 React 前端当作复刻对象。
- 不为了 `open-nwe` 的第一个页面提前发明 DSL。
- 不为了聊天界面提前开启输入框 / IME / 富文本。
- 不为了任务中心提前做完整表格系统。
- 不为了终端 / 编辑器提前进入复杂文本硬仗。
- 不把 `open-nwe` 的产品需求反向污染 P0/P1 的底层真实能力。

更合理的用法是：

- 把 `open-nwe` 当成真实需求压力源。
- 每完成一个 GUI 底座能力，再问它是否能服务 `open-nwe` 的某个产品面。
- 直到仓颉 GUI 具备最小 app shell / 事件 / 布局 / 文本能力前，不做接入计划。

## 5. 未来能力优先级映射

### 第一批：底座能力

这些能力不直接服务完整 `open-nwe`，但没有它们一切免谈：

- 窗口
- 事件循环
- 鼠标 / 键盘事件翻译
- 重绘调度
- GPU 绘制命令
- 最小 Scene / Renderer 边界
- 基础矩形 / 边框 / 圆角 / 颜色

### 第二批：工作台外壳能力

这些能力会开始让 `open-nwe` 的外壳有雏形：

- Box / Stack / Row / Column
- ScrollView
- Panel
- Sidebar
- Button
- Label
- StatusBadge
- List
- Toolbar

### 第三批：复杂产品面能力

这些能力才接近 `open-nwe` 的真实使用需求：

- 文本测量与渲染
- 输入框
- 选择 / 光标
- 流式消息列表
- 表格 / 虚拟列表
- 弹层 / 菜单
- 快捷键
- 日志视图

### 第四批：后期硬仗

这些能力不能提前打开：

- IME
- 富文本编辑
- 代码编辑器
- 终端模拟器
- 无障碍
- 跨平台 backend
- 打包发布体系

## 6. 推荐结论

建议写入仓颉 GUI 项目的长期判断：

> `open-nwe` 是未来真实宿主应用候选，不是当前开发入口。

下一步仍然应该回到仓颉 GUI 本体：

- 先完成 `P1 最小 Scene / Renderer 输入 preflight`
- 再让仓颉描述一个矩形，由 Metal 执行绘制
- 等到基础 layout / event / text 能力出现后，再重新评估 `open-nwe` 的实验性接入

## 7. Stop-line

本文件不批准：

- 修改 `open-nwe`
- 修改仓颉 GUI 运行时代码
- 开始迁移现有 React 前端
- 设计完整 app shell
- 开启输入框 / IME / 富文本 / 终端 / 编辑器
- 以 `open-nwe` 的当前页面结构倒逼仓颉 GUI 公共 API

本文件只批准：

- 把 `open-nwe` 作为 future demand map
- 在后续 GUI 框架设计中，把它作为复杂桌面应用的压力测试样本
