## 二、可选的业务工作会话保存与跨进程恢复

新增的实际能力是：关闭后重开仍能回到应用选择保留的未应用业务草稿，界面文档和业务工作会话各有明确含义。当前mixed按进程重建业务卡片，界面文档重开不是此项验收。

先复用公共表单/owner契约、`shared_text_document_workspace.cj`、`shared_text_document_file.cj`、`composable_ui_ui_document_session.cj`与workspace的已有存储/基线/关闭协调机制。应用定义业务载荷、恢复规则和选用路径，框架只补缺失的通用保存/载入/失败保护与生命周期接缝；已有公共存储足够就直接接通，不硬编码规则/预设字段，不另造数据库、通用业务状态机或第二份AI业务镜像。布局描述、已应用值和未应用草稿不能混成一份隐式Apply。

完整子包至少实现：通过正常菜单/工作区/关闭入口显式保存工作会话；按稳定owner身份保存应用允许保留的草稿、已应用基线、必要版本/选择；新进程正常载入并继续编辑。恢复使用新窗口/端点/票据身份，不能恢复旧native会话或让旧迟到回执覆盖新会话。Apply/Cancel仍执行原业务规则，保留草稿不等于自动应用。文件schema、尺寸预算、损坏、过期或外部改写、失败写入按既有可信基线规则拒绝，不能部分覆盖旧工作状态/文件。

以mixed双owner为完整消费：A与B有不同正文且至少一方dirty → 正常入口保存会话并退出 → 新PID重开 → 公共客户端完整读回草稿/已应用值/dirty与身份 → 人继续输入 → 外部合法操作 → Apply与Cancel → 正常关闭。给出字节和业务版本的独立读回，而非截图或序列化函数自测。Rules或现成UI-only应用只做受影响的复用短链，证明应用定义能替换、未启用该能力仍正常；不重跑两个完整历史矩阵。第二消费者若揭示通用接缝问题，在本包修复，不以复制样例私有状态机过关。
