# 仓颉 GUI 框架思考框架

Last updated: 2026-04-24

Nature: docs-only / governance-assist / project-thinking framework  
Status: reference-only  
Scope: 用于指导“仓颉原生 GUI 框架”项目的架构判断、任务选择、边界治理与阶段推进

## 0. 非执行声明

本文不是实现计划，不直接创建代码任务，不直接修改 runtime、API、平台桥接、目录结构或构建系统。

本文的作用只有一个：

- 把你在 `open-nwe` 项目里使用的复杂系统思考框架，抽象为适用于“仓颉 GUI 框架”项目的判断语言。

它服务的是：

- 我们如何判断下一步做什么
- 我们如何避免过度设计
- 我们如何保持初心不变
- 我们如何在长期项目里不跑偏

它不服务的是：

- 立刻创建一个“元逻辑模块”
- 把思考框架实体化成 runtime owner
- 用抽象概念替代具体技术判断

## 1. 这份框架要解决什么问题

我们现在要做的不是普通应用开发，而是：

- 为仓颉补一块长期缺失的 GUI 基础设施
- 尽量不依赖重型外部 GUI 框架
- 让未来个人桌面应用开发更容易
- 在“为爱发电”的前提下，仍然保持工程秩序

这种项目最容易出现三类问题：

- 一开始就想做太大，直接冲向“仓颉版 Qt”
- 因为追求纯粹而否认底层平台现实
- 为了赶进度不断打补丁，最后没有真正的框架骨架

所以这份框架的核心目标是：

> 帮助我们持续选择最窄、最真的下一刀，并防止项目在抽象、平台、依赖、节奏、野心上失控。

## 2. 从原项目框架到 GUI 项目的概念映射

原项目中的很多概念是业务系统专属的，不能直接照搬。下面是我们在 GUI 项目中的对应关系。

| 原框架概念 | GUI 项目中的对应含义 |
| --- | --- |
| Mission | GUI 框架当前阶段目标 / 当前里程碑 |
| Mission truth owner | 当前能力所属的核心模块 owner |
| ExecutionProfile / ApprovalPolicy | 平台能力边界 / 依赖边界 / 允许的技术路径 |
| Tool / Provider readiness | 平台 backend readiness / 桥接能力 readiness |
| Route / UI read surface | 对开发者公开的 API、示例、文档、DSL、样例程序 |
| Projection 不能成为 truth | demo / example / DSL 不能反向发明底层 runtime 真相 |
| Narrow slice | 只做当前能闭环验证的一小块能力 |
| Replay / idempotency / audit | 事件、渲染、状态流、平台桥接的可验证性和可追踪性 |

这意味着：

- 我们不再关心 `MissionManager` 之类的业务 owner
- 我们关心的是 `platform / runtime / layout / render / widgets / state`
- 我们不再关心 API 产品治理
- 我们关心的是“公共 GUI API 是否建立在真实底座之上”

## 3. GUI 项目的总宪法

### 3.1 根目标

我们的根目标不是“显得会做 GUI”，而是：

> 先做出一个仓颉桌面运行时，再让它逐步长成一个小而真、可持续演化的 GUI 框架。

### 3.2 当前初心

- 不依赖重型外部 GUI 框架
- 上层尽量保持仓颉原生
- 底层允许必要的平台桥接，但向上接口必须极窄
- 先求结构真实，再求功能丰富

### 3.3 当前现实边界

- “绝对纯仓颉、零桥接”不可行
- “不依赖 Qt/GTK/Electron，核心框架层由仓颉实现”可行
- 操作系统窗口、事件循环、图形上下文最终必须落到平台原生能力

### 3.4 项目成功标准

成功不等于功能最多。

更重要的是：

- owner 清楚
- 分层清楚
- 每一层的真相源清楚
- 能够小步验证
- 能够长期追加能力而不推倒重来

## 4. GUI 框架的三层治理

任何新能力建设、任何大改动，在开工前都先看三层：

- `入口层（Ingress）`
- `执行层（Execution）`
- `真相层（Truth）`

### 4.1 入口层

入口层指对框架使用者暴露的东西：

- 开发者 API
- Widget API
- 组件声明方式
- DSL
- 示例程序
- 文档中的用法

纪律：

- 入口层只能消费底层真实能力
- 不允许入口层为了“演示好看”先发明不存在的能力
- 不允许 demo 成为架构真相

### 4.2 执行层

执行层指真正跑起来的系统：

- 窗口创建
- 事件循环
- 事件分发
- 状态更新
- 布局计算
- 绘制与重绘
- 平台资源生命周期

纪律：

- 执行层必须有单一 owner
- 执行链必须清楚
- 不允许多条路径同时解释同一动作

### 4.3 真相层

真相层是我们最需要守住的部分。

在 GUI 项目里，真相通常包括：

- 当前 UI 状态树
- 当前布局结果
- 当前渲染命令或渲染输入
- 当前平台对象生命周期

纪律：

- docs、示例、DSL、调试输出都不能自造第二真相
- 平台回调只负责反馈，不直接成为高层真相 owner
- 渲染结果不能反向定义状态真相

## 5. GUI 项目的统一元逻辑循环

沿用你原来的骨架，但翻译到 GUI 项目中：

> 观局 -> 定位 -> 取势 -> 行动 -> 反馈 -> 调整 -> 复归

### 5.1 观局

先看真实盘面。

需要先问：

- 当前项目处在哪个阶段：底座、补洞、扩控件，还是追求易用性？
- 当前最缺的是窗口、事件、绘制、布局，还是控件？
- 当前平台桥接能力是否已足够？
- 当前问题是真问题，还是我们被更远的野心吸走了？

### 5.2 定位

先确认当前问题属于哪一层、哪个 owner。

需要先问：

- 这是入口层问题，还是执行层问题，还是真相层问题？
- 当前 owner 是 `platform`、`runtime`、`layout`、`render`、`widgets`，还是 `state`？
- 这次改动会不会让两个模块同时解释同一件事？

### 5.3 取势

选择当前最窄、最合法、最低风险的一条路径。

需要先问：

- 哪条路径最容易闭环验证？
- 有没有更薄的切口？
- 这是“基础设施必经之路”，还是“看上去高级的捷径”？
- 我们该先补底座，还是已经可以上层抽象？

### 5.4 行动

只在边界内推进。

需要先问：

- 这次动作是否有明确 owner？
- 是否有最小 demo 或最小验证？
- 会不会改变公共 API？
- 如果失败，能否清楚回退？

### 5.5 反馈

行动后要看真实结果，而不是看想象。

需要先问：

- 功能是否真的跑通？
- 这次改动让架构更清晰，还是更混乱？
- 是否出现平台层和框架层互相夺权？
- 是否产生“示例能跑，但基础不稳”的假象？

### 5.6 调整

根据反馈改变路径，而不是机械推进。

需要先问：

- 当前阶段目标是否仍成立？
- 是否需要缩小切口？
- 是否已经开始跨出本轮 blast radius？
- 是否该暂停扩张，先补结构？

### 5.7 复归

最后回到初心。

需要先问：

- 这一步是否真的服务于“做出仓颉 GUI 底座”？
- 这一步是在修骨架，还是在堆功能幻觉？
- 这一步是否让未来开发桌面应用更容易？
- 是否有不必要的抽象和扩张？

## 6. 最小可用原则集

如果把这套框架压缩成一组我们长期反复使用的原则，先保留这 12 条。

1. **先做桌面运行时，再做 GUI 框架**
   窗口、事件、绘制、状态是底座，控件和 DSL 是上层。

2. **先单平台跑通，再谈跨平台**
   没有一个稳定 backend 之前，不做漂亮的跨平台抽象。

3. **上层尽量纯仓颉，底层只留最薄桥接**
   追求的是“最小平台依赖”，不是否认平台存在。

4. **单一 owner，单向投影**
   Widget API、示例、文档只能投影底座能力，不能发明第二真相。

5. **低阻力路径必须先是合法路径**
   简单不等于正确，捷径不能破坏结构。

6. **优先修基础闭环，不优先追求视觉效果**
   一个稳定的窗口循环，比十个好看的按钮更重要。

7. **反馈为真**
   实机结果、事件流、重绘行为、资源生命周期比抽象叙述更可信。

8. **过犹不及**
   不要过早做跨平台、文本输入、DSL、热重载、主题系统。

9. **文本、输入法、无障碍属于后期硬仗**
   它们不是“顺手补一下”的级别。

10. **示例不等于能力成熟**
    跑出一个 demo，不代表架构已经可持续。

11. **不以纯粹之名拒绝现实**
    GUI 框架必须尊重平台窗口系统、事件系统和图形上下文。

12. **复归本心**
    我们做的是仓颉 GUI 基座，不是展示架构野心。

## 7. 不能做的误用

### 7.1 不能一开始就做“仓颉版 Qt”

错误表现：

- 一开局就设计完整控件体系、主题系统、动画系统、布局系统、DSL、热重载
- 还没跑通窗口和重绘，就开始讨论生态位

正确边界：

> 第一阶段先做桌面运行时，不做全功能 GUI 王国。

### 7.2 不能把跨平台抽象做在单平台能力之前

错误表现：

- 还没有一个 backend 稳定，就开始抽象 `WindowBackend`、`RenderBackend`、`TextBackend`
- 抽象先于真实经验，导致公共 API 被平台猜想污染

正确边界：

> 至少先有一个真实跑通的平台实现，再决定哪些抽象值得升到公共层。

### 7.3 不能把 demo 当成真相源

错误表现：

- demo 能点击，就认为事件系统没问题
- demo 能显示，就认为渲染模型已经正确
- 示例 API 先行，逼着底层去适配演示代码

正确边界：

> demo 只能证明现象，不能定义架构真相。

### 7.4 不能让平台桥接反向污染公共 API

错误表现：

- 某平台的临时 workaround 直接暴露到开发者 API
- 平台私有对象泄露到高层接口

正确边界：

> 平台桥接应尽量留在底层，不能把平台偶然性固化成框架公共契约。

### 7.5 不能把“纯仓颉”理解成“拒绝薄桥接”

错误表现：

- 因为追求纯粹，拒绝使用最小平台桥
- 结果不得不依赖更重、更绕的曲线方案

正确边界：

> 真正的纯度是上层框架逻辑可控，而不是物理上不接任何平台能力。

### 7.6 不能太早碰文本输入、IME、复杂文本系统

错误表现：

- 第一阶段就做 `Input`
- 还没稳定事件和绘制，就进入光标、选区、输入法、文本 shaping

正确边界：

> `Text` 可以早一点，`Input` 必须晚一点。

### 7.7 不能让“取势”变成分析成瘾

错误表现：

- 一直讨论路线，不进入最小实现
- 任何小问题都扩成系统级研究

正确边界：

> 当信息足够支撑最小闭环决策时，应进入行动。

### 7.8 不能让“为爱发电”成为随意打补丁的理由

错误表现：

- 觉得反正不是商用，就接受结构腐化
- 明知架构不对，也用局部补丁硬推

正确边界：

> 为爱发电更需要珍惜结构，不该用热情为混乱背书。

## 8. GUI 项目的当前推荐切口

如果把这套框架落回到当前项目现实，我推荐的第一阶段切口仍然是：

> `macOS single-platform desktop runtime first slice`

### 8.1 第一阶段只做

- 创建窗口
- 事件循环
- 重绘触发
- 鼠标事件
- 键盘事件
- 画矩形
- 画最小文字

### 8.2 第一阶段明确不做

- 跨平台
- 输入框
- 输入法
- 富文本
- 无障碍
- 主题系统
- 热重载
- 完整声明式 DSL
- 大而全控件库

### 8.3 第一阶段成功信号

- 能稳定打开窗口
- 事件流清楚
- 重绘行为可预测
- 桥接层足够薄
- 上层仓颉代码已经开始承载真正逻辑

### 8.4 第一阶段走偏信号

- 开始讨论完整跨平台抽象
- 为了“优雅”跳过实机验证
- 为了“纯粹”拒绝最小桥接
- 过早进入输入框、复杂文本、动画系统
- demo 先行，底座滞后

## 9. 从思考框架到工程能力的迁移路线

这套框架不应该永远只停留在聊天里，但也不应该一开始就变成新的 runtime 模块。

更稳的路线是：

### 9.1 第一阶段：作为人类与 AI 的判断语言

用途：

- 选下一步任务
- 判断是否过度设计
- 判断是否越界
- 判断当前 stop-line 是否该保持

### 9.2 第二阶段：脱水为项目文档和任务节奏

用途：

- 形成稳定的阶段目标文档
- 形成 narrow slice 任务定义方式
- 形成每轮开工前的检查点

### 9.3 第三阶段：沉淀进现有 owner，而不是新建“哲学模块”

例如：

- 平台能力边界进入 `platform` 文档
- 状态真相进入 `runtime/state`
- 布局真相进入 `layout`
- 绘制真相进入 `render`
- 公共 API 边界进入 `widgets` 或 `api`

### 9.4 第四阶段：只有反复出现的稳定问题，才考虑新模块

例如未来真的多次撞到，才考虑：

- `text system`
- `input system`
- `observation cadence policy`
- `objective/versioned roadmap`

新模块必须解决稳定工程问题，而不是实体化一个抽象概念。

## 10. 我们后续每次开工前的轻量检查点

以后如果我们继续推进 GUI 框架，每次开工前先快速回答 6 个问题：

1. 当前要解决的是哪一层的问题？
2. 当前 owner 是谁？
3. 这一步是不是最窄切口？
4. 这一步会不会制造第二真相源？
5. 这一步能否用最小 demo 验证？
6. 这一步是否仍服务于“仓颉 GUI 底座”而不是别的野心？

## 11. 当前结论

这套从 `open-nwe` 抽象出来的框架，对 GUI 项目是适用的。

但适用的不是它的业务术语，而是它背后的骨架：

- 单一 owner
- 单向投影
- 真相层治理
- 任务选择优于任务堆积
- 窄缝推进
- 反馈驱动
- 复归初心

如果把它翻译成一句最适合我们 GUI 项目的话，就是：

> 先守住底座真相，再用最窄的切口让框架一点点长出来。
