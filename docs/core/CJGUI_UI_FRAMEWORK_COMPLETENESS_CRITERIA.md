# CJGUI 可用性与验收

更新：2026-09-12。当前方向的验收依据；不要求每个阶段完成完整 GUI 框架。

## 规划大阶段时的完整性视角

最小共同操作验收只是框架的一条能力链。选择下一阶段时，还应对照以下主线；不要求每项同步开工或逐轮打分：

- 开发者用仓颉组合组件、布局、样式和资源，能更换界面结构与业务含义。
- 场景、绘制命令、自绘后端和更新机制逐步接通，系统桥接承载必要平台服务。
- 人的点击、键盘、焦点、滚动、文本与无障碍具备正常应用证据。
- 人与外部系统理解对应内容和关系，能可靠执行、解释失败并接续工作。
- 普通包消费、调试与错误反馈可以复现；轻量和效率有实际观测依据。

从[设计意图与资产导航](../plans/DESIGN_INTENT_INDEX.md)查已有实现、原型和退役入口。样例增加功能后，应能解释哪项能力可被其他应用复用；不能把固定编辑器完备度等同于通用框架完备度。

## 最小共同操作阶段

需要同时证明：
1. 独立样例通过正常包/库入口消费 CJGUI，启动真实窗口并清楚显示内容。
2. 人通过真实输入选择或修改内容，状态与画面对应更新。
3. 外部客户端能读取对应对象与当前选择，并在授权范围内完成实际操作。
4. 外部修改出现在应用实际内容和窗口中；人继续修改后，外部端能获取新状态。
5. 过期请求不会静默覆盖人的新修改，失败不会显示为成功。
6. 一次真实模型/Agent 通过同一路径完成操作；测试客户端不能冒充这一证据。
7. 运行入口、必要设置和已知限制能让下一位开发者复现。

列表可以作为首个中性样例；不固定最终产品或要求聊天框。
少量基础控件即可，不要求首阶段具备完整文章编辑、IME、白板或跨平台能力。
模型接入环境缺失时标记外部实测缺口，不把前五项通过写成全阶段完成。

## 证据用词

| 状态 | 能说明什么 |
| --- | --- |
| 设计 | 有约定，无运行结论 |
| 源码存在 | 找得到实现，未必构建或运行 |
| 针对性通过 | 指定探针/测试通过，范围以实际执行为准 |
| 应用已集成 | 正常样例消费框架、真实输入与显示已验证 |
| 外部接口已验证 | 独立客户端实际操作应用，未必有模型参与 |
| 共同操作已验证 | 人与真实外部智能系统已在同一应用里接续操作 |
| 已发布 | 有实际包/版本与发布证据，不能由前面状态推导 |

## 后续检验

首阶段之后，用另一种独立样例检查复用，避免第一款应用的私有结构决定框架。
逐步增加编辑、复杂文本、无障碍、布局、样式及可选生成能力，由真实使用需求排序。
效率评估比较完成整件事的耗时、错误、检查与接手成本，并记录应用开发者的重复接入代码。
采用相同任务和模型，与设计良好的 GUI 加结构化接口比较；只超过截图操作不足以证明框架优势。

探针、静态图、截图和模型回复各有用途，都不能单独证明完整链路。
