# DS48 施工图：把运行时界面能力交给普通开发者

日期：2026-10-23。性质：指导下发的下一整阶段设计与实施依据；写入本文不代表已经开工或实现。用户把本文交给 DS 启动 goal 后，按整包连续执行。当前状态只更新 [ACTIVE](../../runtime/cjgui/ACTIVE_DIRECTION.md) 的 DS 段，不再建立执行卡或第二份进度表。

## 1. 最终要交付什么

让一个普通开发者拿到唯一 SDK 后，能够：

1. 用仓颉声明自己的对象、字段、规则和动作，手写界面、生成界面和公开读写复用这些定义。
2. 在运行中的应用内组合已有 Tabs、滚动区、分栏、字段与可搜索 Select；定义两个有真实用途的组合，在一个候选中同时创建或更新，再分别绑定不同对象。
3. 把已接受的界面保存成可读、可复用的界面文档。在同一应用的新会话中载入，重新核对当前能力和绑定，通过新的候选事务接受；界面描述不携带旧会话权限，也不覆盖业务草稿。
4. 人在界面中编辑，外部调用方修改布局、呈现与组件定义，人直接继续编辑；非法修改保留当前可用界面。运行时能表达的修改不要求重新编译或重启。
5. 使用公共 API/CLI 完成发现、预览、保存计划、提交、票据查询和读回；普通使用不需要从历史聊天抄私有脚本、补 SDK 文件或硬编码打印业务命令。

这是一包“开发、运行时迭代和交付”的完整工作。新增的关键能力是**多定义原子提交、可复用界面文档、低重复接线的多对象接入，以及已有工作区组件的公共接通**。最后用两个业务证明它们能合在一起使用。

第一成熟版的窗口连续性、普通负载长阻塞与资源责任仍由 Sol 推进。本包不会仅凭客户端和示例通过宣布整个框架成熟，也不以等待 Sol 所有问题结束为开工条件。

## 4. 施工前先分清六种事实

| 事实 | 权威来源 | 容易犯的错误 |
| --- | --- | --- |
| 组件/字段/动作/资源是否可用 | 当前应用注册与准入目录 | 客户端支持某格式，就称端点支持；未发布的事实猜成支持。 |
| 组合定义和界面结构 | 已接受的 region 结构与定义目录 | 将候选暂存内容用于公开发现，或失败时清掉旧 accepted。 |
| 业务值、草稿、规则、Apply | 原 owner 及其版本/事务 | 用结构更新顺便写业务值；把 UI 初值当作新的业务真相。 |
| 当前实例绑定 | accepted instanceKey、owner target、incarnation | 同 key 换绑后沿用旧会话；重新解析后把迟到输入投给新 owner。 |
| 焦点、选区、视口 | 原窗口/会话与 holder 的合法状态 | 在模板里靠延时、补点击、重发恢复，或每次改布局清空这些状态。 |
| 提交结果与可见进度 | 原候选票据、接受版本及场景事实 | submit 返回就说已显示；超时改叫 rejected；查询票据又提交一次。 |

两项特别说明：

- `applied=false` 如果处在 BOOLEAN 字段值里，表示已应用的值为 false；是否执行成功要看动作回执和前后版本。不要再把它当 Apply 失败。
- 多个 owner 各自的精确读回是有用且正确的能力。本包不新增跨 owner 一致快照或跨 owner 业务提交；不得把多次读包装成一个原子字段快照。

## 5. 第一阶段：多定义的一次候选事务

### 5.1 为什么先做它

现在 accepted 目录能有多个定义，客户端也能读完整目录，但生产候选解码和编辑计划仍限“一次改一个定义”。这导致保存了两个组合的完整界面，也不能在新会话里一次恢复；按顺序提交会出现部分更新和中间界面。

本阶段将“定义 A、定义 B、删除旧定义、实例/布局变化”放进**原有一个候选票据**。不用新的票据系统，不把普通草稿纳入结构事务。

### 5.2 直接入口

- [运行时组合](../../runtime/cjgui/src/composable_ui_runtime_composition.cj)：`CjguiCompositionDecodeResult`、`cjguiRuntimeCompositionDecode`、定义验证/编码和通用工厂。当前 decode 持一个 optional definition，第二段 COMPOSITION 会被拒。
- [生成核心](../../runtime/cjgui/src/composable_ui_generated.cj)：`snapshotStagedComposites`、`restoreStagedComposites`、stage/commit/rollback、`acceptedCompositionPayload`、`CjguiGeneratedUiEncoding` 解码。
- [region](../../runtime/cjgui/src/composable_ui_generated_region.cj) 的提交/结算，以及 [rules provider](../../runtime/cjgui/examples/rule_set_window_app/src/rule_set_generated.cj) 的同一接缝。
- [typed client](../../runtime/cjgui/shared_operation_core/cjgui_generated_client.py) 的 document 编解码、[editor](../../runtime/cjgui/shared_operation_core/cjgui_generated_edit.py) 的 touched definitions、预览、保存计划和精确读回。

### 5.3 明确的事务语义

继续使用现有 v2 的 COMPOSITION/CPARAM/CELEMENT/CTEMPLATE/COMPOSITION_END/REMOVE 与 NODE/PROPERTY/END。新候选允许多个完整定义段；每段必须有自己的 END。旧 v1、旧单定义 v2 与旧 saved plan 按兼容分支保留。

用现有 catalog 的同一准入数据发布“候选允许的定义数量和预算”。这是新增公开事实，不另维护一张客户端假想能力表。具体记录名随现有编码风格确定，生产、解析、文档一起落地；缺少该事实的旧端点，客户端仍按旧的一定义能力处理，不能乐观发多定义。

逻辑应等价于：

```text
读取一次 accepted 基线 S 和版本 v
解析完整候选；检查名字、段边界、类型、总量
构成候选目录 S'：
  未提及的定义保留
  同名定义整段替换
  显式 REMOVE 删除
用 S' 验证本候选全部实例、字段/动作引用、结构和展开总量
通过才进入原 candidate 暂存/场景路径
场景接受：一次发布定义目录 + 结构 + 实例，并结算原票据
拒绝/取消：不发布 S'，旧 accepted 保持
```

不得只在循环末尾返回错误，却已把前几个定义写进 accepted。需要恢复的暂存快照用现有机制；不要为每个定义另建一个待接受事务。

必须守住：

- 同一候选重复定义、重复 REMOVE、同名定义又 REMOVE：具名拒绝，不用“最后一个赢”。
- 删除后仍有实例引用该定义：整候选拒绝。删除定义和全部引用实例可在同一候选完成。
- 坏定义 B 不能让本候选中的 A 提前生效；非法后来候选不能破坏此前合法 pending 候选的暂存目录。合法新候选替代旧 pending 沿原契约退休。
- 除每定义模板/深度/参数预算，还要在分配与展开前约束候选总字节、定义总数和最终展开规模。上限由 catalog 明确配置和发布；本包实际链至少同时提交两个定义，不靠无限放宽预算通过。
- 本包仍不做组合递归、组合嵌套或脚本。多个同级定义已经足够解决恢复完整界面的实际问题。

### 5.4 客户端和读回一起完成

将编辑器“一次 touched 一个定义”的内部值扩成有序集合；多定义编辑在一次 preview 得到一个 candidate 与完整 expected accepted state。批次有任何不合法操作，零提交。

继续区分 `submitted_sha256`（本次 delta）和 `expected_structure_sha256`（完整 accepted 状态）。定义目录可以按稳定名称顺序规范化；模板树、子节点次序和操作顺序有语义，不能为摘要一致随意排序。未知 token/声明行的 lossy 守卫保持。

保持 saved plan 的端点、基线版本、完整摘要与预览核对。若数据表示确需新格式版本，显式新增版本并保留旧 v1 的验证读取；不要改旧版本含义，也不要删预览校验求兼容。`status/resume` 仍是只读原票据。

**本阶段结束点：** 两个定义和实例一次接受、一次失败全保旧，以及完整原子结构读回已成立，随后继续第二阶段；不用先导出 SDK 或让指导逐条验收。

## 6. 第二阶段：保存和载入可复用的界面文档

### 6.1 界面文档不是旧计划改个名字

| 文档 | 用途与约束 |
| --- | --- |
| 保存计划 | 某端点、某版本、某完整基线上的待执行修改。过期就拒绝，不能搬到新端点继续执行。 |
| 回执 | 某次真实提交的票据和已观察结果。status/resume 只能查询，不能重提。 |
| 本包界面文档 | 可重新实例化的布局、组合定义及声明引用。导入时在当前端点重新发现、校验、预览，生成一个新的计划。 |

在现有 typed document 上提供一层很薄的文件封装，公开 API 与 CLI 共用。建议名称 `cjgui.ui-document` v1；这是本阶段拟实现的格式，不是宣称已经存在。

内容包含完整无损 v2 结构文档、明确的格式版本、结构摘要，以及从实际引用派生的组件/字段/动作/样式/资源需求。不要复制全部 capability catalog，更不要把需求清单作为权限依据。

不包含 endpoint/socket、ticket、当前 structureVersion、原生 nodeId、incarnation、选区、焦点、草稿/已应用值、授权 token、绝对临时路径。稳定实例 key、字段名、动作名和资源 key 属于声明，可保存。纯标签、布局参数和声明的 UI 默认值保留，不得借此写 owner。

### 6.2 导出和导入过程

导出：从**同一次 accepted snapshot**读取完整定义和节点，确认可无损解析后编码。保存时不把正在 pending 的候选拼进去。文件写入用同目录临时文件完成后原子替换；失败保留旧文件。明确保存路径，不能后台替用户覆盖别的文件。

导入：

1. 有界读取、校验格式/摘要/结构；未知或有损内容只能查看，不能悄悄丢弃后执行。
2. 刷新当前 endpoint 身份与 capability；使用当前声明解析实例 key 和字段/动作引用。持久文件不是授权证明。
3. 从当前 accepted 基线计算一个新的计划，显示新增/替换/删除的定义与节点，以及实例绑定会保留还是变化。
4. 通过原 submit/CAS/ticket 路径执行。发生并发修改，返回 stale；不自动换基线重放。调用者可以明确要求重新预览并创建新计划。
5. 接受后完整读回；超时且有票据保存回执，后续查询不重提。失败后继续使用原界面。

公共入口至少有“导出当前界面、导入预览、执行导入计划”。命名按现有 API/CLI 风格；指南应同时给可导入 Python 调用和命令行示例，不要求调用私有校验函数。

默认导入采用**合并定义 + 替换该开放区域节点树**：未提及的 accepted 定义沿当前契约保留。另提供显式“替换该区域完整运行时定义集”，其 REMOVE 列表从当前 accepted 基线计算并在预览中明示；不能删除编译注册的组件，也不能暗中修改区域外的手写界面。两者都在一个候选完成。

本包的可迁移范围是：同一业务能力契约的另一次会话/另一个实例。跨不同业务不靠相似标签自动匹配字段，不将打印 owner 6301 搬成规则 owner 1。缺少声明或资源 key 就给具体拒绝；调用者需要改变绑定时，使用已有稳定 key 编辑操作明确修改文档，再重新预览。暂不引入通用字段映射语言。

### 6.3 在正常应用里消费

让包外 mixed 和 rules 都能在启动时选择一个界面文档，原有不带文档的启动方式保持。运行中导入/导出以公共 API/CLI 为基础，正常应用中提供可发现的入口或使用说明；已有路径输入与命令机制足够时，不为此新造原生文件对话框。

界面资产可以从相对路径加载，路径基于应用明确的资源/工作目录解析，不依赖执行时恰好在仓库根目录。坏文件、缺依赖、超预算必须给可读错误，并保留原默认界面；不得加载了一半后继续画默认值。

**结束点：** 同一进程导出/改版/载入保留草稿；正常关闭后在新端点载入同一文档成功；旧 saved plan 在新端点仍拒绝。重开是验证资产可复用，不冒充零重启修改链。

## 7. 第三阶段：让已有工作区组件容易被手写和生成界面共用

### 7.1 先接已有能力

[生成核心](../../runtime/cjgui/src/composable_ui_generated.cj)已有 `CjguiGeneratedUiPresentation`、`tabsContentProperties`、`tabPageContentProperties`、`splitContentProperties`、`scrollContentProperties`、`imageContentProperties` 和对应工厂/状态。`CjguiGeneratedUiFormBinding.capabilityCatalog()` 则是刻意保守的表单词汇，不能因为它没默认注册全部组件就重新实现这些控件。

提供一个**可选的公共注册组合**，把 Tabs/tabPage、ScrollArea、Split 和应用已声明的 Image 接入现有 catalog。普通表单默认保持轻量；应用明确选用才注册，图片/字体等资源仍由应用声明。复用各组件自己的属性规格、校验和 presentation，不在 helper 中复制另一套允许列表。

本包正常工作区：一个手写导航/命令外壳，生成区域包含可调分栏，左侧对象/摘要，右侧页签与可滚动详情；两种运行时组合用于“编辑字段区”和“状态/动作区”。两者是同级组合，不借场景需求扩成嵌套解释器。标题/标签/错误和控件来自同一字段/反馈声明。

### 7.2 更新与交互

- 兼容改 gap、padding、标签、命名样式、重排时，实例 key 和 owner 不变；复用 holder 的 viewport、tabs、split 状态。不要每次 build 重新构造状态把人的位置抹掉。
- 需要修改默认视口或页签时，沿已有声明/交互规则区分“初始值”和“显式重置”；不为了让新文档看起来生效，全部强制回顶或切第一页。
- 通过外层普通 NODE 组合已有控件。只有真实文档确实无法表达、且已有工厂能复用时才补窄模板接缝；不趁机给 CTEMPLATE 复制完整 NODE 语言。
- Select/Radio/Segmented 继续消费同一 choice binding，选项的 key、值和显示文字分清；高亮和查询不写业务，确认才执行当前 owner 事务。
- 锁定、删除、换绑使旧弹层失效时，继续复用既有 guard 与 layer 结束路径。候选不存在 trigger 时不能留下坏锚点拒绝整场景。
- 只读/禁用/错误及原因要同时可见、可查询，不能只灰显而外部仍可写；也不能因为区域看不见就拒绝原本已授权的业务调用。

本阶段至少在正常工作区完成：缩窄后内容可达、拖分栏、切页签、滚动到低位字段、键盘 reveal、Select 搜索确认/取消，运行中重排后继续编辑。大部分机制已有，不为每个控件重跑一套历史矩阵。

## 8. 第四阶段：降低多对象接入和共同定义的成本

### 8.1 先消掉哪类重复

当前 [MixedPresetProvider](../../runtime/cjgui/templates/macos_application/mixed_form/src/preset_cards.cj)要重复转发 draft、availability、field/action target、range/CAS/rebase 等；[规则 provider](../../runtime/cjgui/examples/rule_set_window_app/src/rule_set_generated.cj)也有实例路由。它们的业务不同，但“解析对象后委托已有 form binding”的胶水应尽量复用。

先比较两处实际重复，抽出薄的多对象 form-binding 适配入口：应用负责把一个声明实例 key 解析到自己的既有对象/单 owner binding；框架负责一致转发读取、可用性、意图、动作和范围会话。优先组合 `CjguiGeneratedUiFormBinding`、`CjguiFormFeedbackProjection` 与现有 region binding，不新造 domain、草稿表或版本计数器。

具体类名由实现确定，但职责不能糊成“万能数据表单”。业务 owner、授权、持久化和规则仍是应用代码；旧自定义 provider 可继续使用，不强迫所有消费者迁移。

需要严格区分普通节点 key、声明的对象 instanceKey 和空实例的旧单 owner 路径。不要把当前 mixed 的 `startsWith("card")` 提升成框架规则，也不要粗暴禁止所有非空节点 key。对象命名/解析由应用明确声明；未知或退休的**对象实例**不能回落到默认 owner。

### 8.2 绑定身份与一次读取

每次 dispatch 都以 accepted 中冻结的 owner target/incarnation 检验当前解析结果。不能把旧事件的 key 再解析一次，恰好找到新对象就写进去。新对象使用新的合法会话。

一次对象字段投影使用一份该 owner 的 formFeedback/snapshot；BOOLEAN 首次构建、刷新和呈现切换都优先冻结反馈，不能一边用快照一边读 live 值。range bridge 的五个旧重载、版本 CAS、confirm、rebase 及历史不足返回 None 保持原契约。

公开读回直接使用已有：

```python
session.snapshot()                       # 原子结构/实例与已声明字段范围
session.form_state(instance_key="...")    # 一个指定对象自己的字段/动作投影
session.fields(owner_resource_id=...)    # 已授权的 owner 定向字段
```

这些调用已经存在，本包补消费者/教程接线。需要将结构与对象读回关联时，记录各自版本与 owner 身份；若绑定期间变化，具名说明并重新获取一次当前上下文，不伪装成跨对象原子快照。不得为了通过改为直接读取应用内存或私有 cards 表。

### 8.3 必须做一次真实的“改业务”验收

在 rules 正常消费者上添加一个有实际行为的新字段，建议“备注说明” TEXT：有真实草稿、长度规则、Apply/Cancel 和持久化；若该字段已存在，则选一个仍有用途的等价字段，不为测试造无意义计数。

要求是**一处业务声明与规则来源**，不要求零业务代码：

- 存储、草稿、应用/取消、序列化是应用必要工作，可分模块。
- 手写布局、生成结构分别引用字段是正常布局代码。
- 不能再增加一份 AI 字段表、一份 generated 校验上限或一套绕过原 writer 的动作。
- 旧规则文件仍可读，新字段有明确默认；保存新格式时显式版本化或按既有兼容扩展规则，不破坏旧样本。

然后只改共同规则来源一次，例如说明长度上限从 80 到 160；重建业务代码是允许的。三入口都应反映新范围，原来合法/非法边界随同一规则改变。这个改规则步骤与“零重启布局修改”分开报告，不能声称业务代码也在热更新。

再把同一 BOOLEAN 字段在手写/生成/组合之间切换 Select 与已有 Radio/Segmented 呈现，不复制选项、可用性或写入规则。以真实读回和失败原因为准，不能只看目录显示的约束。

**结束点：** 两个业务实际使用公共接缝，新字段/规则改动的新增位置可解释；不再需要复制一段完整多对象 provider 才能接第二业务。

## 9. 第五阶段：真实外部使用和开发者入口

将前四阶段做成一条从 SDK 文档就能完成的用法，不再新增只供本次验收的私有工具。

公共编辑示例支持：发现 → 选取公开事实 → 预览多定义计划 → 保存/新进程执行 → 查询原票据 → 导出界面文档 → 新端点预览/载入。参数、帮助、退出码、无票据时不报已保存、迟到查询不重提全部沿现有机制。

新手路线应有三条清晰入口：只写 UI；手写外壳加运行时开放区域；从已保存界面文档启动。可以是同一创建脚本的模式/参数，不复制三套宿主和 runner。先复用现有 mixed-form/ui-only 建项；模板业务展示可简化，但不能删除已有正确性和正常消费入口来换行数下降。

### 一次真正由执行模型完成的公开操作

DS 自己作为外部智能系统，在最终正常应用已启动且有用户草稿时，读取公开 catalog/结构/实例，根据下列目标自行生成一个此前未预写的修改：

> 把当前详情分成“基本”和“高级”两页，把布尔字段换成可搜索选择，在低位增加来自现有 owner 的状态说明；保留 A/B 的未应用草稿和对象绑定，再把两个组合的间距与标题一起调整。

只用已发布能力和本包公共编辑入口，不能直接替换消费者源码、调用私有脚本或把固定测试 JSON 当成模型现场规划。记录目标、实际发现结果和这次公开工具调用即可；不需要新模型服务、聊天壳或外部顾问。若当前执行工具只能运行预写链而没有这个真实推理/操作过程，就如实记脚本消费，不伪造模型证据。

随后用系统真实输入通道在改后的字段续写、Select 取消和确认、Apply，再公开精确读回。AX 动作、HID/键盘、事件级注入分别标明；不能在需要输入完成语义的步骤用直接 owner 写入替代。

本阶段不建立可视化设计器、拖拽画布、任意代码执行或自动生成业务实现。

## 10. 第六阶段：统一验收、SDK 与交付

### 10.1 先做少量能区分错误的反例

不是每项各起一个应用。纯协议/编码用现有单测和最小 harness；真实窗口集中到最终连续链。

| 问题 | 必须能区分的证据 |
| --- | --- |
| 多定义部分提交 | A 合法、B 非法时整批零发布；合法 A+B 一票据/一结构版本；pending A 遇非法后来候选保留。 |
| 删除与恢复 | 删除定义且保留引用拒绝；同批删引用和定义成功；文档替换预览明确列 REMOVE。 |
| 旧协议/有损 | 旧 v1、单定义 v2、旧 saved plan 可读；未知记录不能静默丢；旧端点没多定义事实时不偷偷拆批。 |
| 资产与旧计划混淆 | 同一资产在新端点重新导入可用；旧保存计划在新端点拒绝；缺声明/资源与坏文件零提交。 |
| 绑定和反馈 | A/B 相同正文/版本但不同 owner 仍隔离；换绑/删除后旧事件拒绝；反馈 BOOLEAN 与 live 相反时只用冻结事实。 |
| 跨进程结果 | 保存→新进程 apply→status/resume；超时真实票据仍保存，查询不增加提交次数。 |
| 业务同源 | 新字段从 UI/生成/外部进入同一 writer；锁定/规则变化后旧可用性不能绕过当前拒绝。 |

这些反例随代码改动运行，已有等价绿证直接复用。不要为了扩大数量再编一批镜像实现的测试。

### 10.2 最终同候选的正常链

从最终冻结输入构建一个包外 mixed 应用，正常运行：

1. A/B 不同 owner 各有未应用草稿，公开确认身份。
2. 一次提交两个新组合和工作区布局；人输入未丢失。
3. 真输入 A，Select 查询/Esc 零写，再确认实际变值；B 独立编辑。
4. 保持焦点和合法选区，运行中同时改两个定义、重排和呈现；立即续写命中原 owner 和合法范围。
5. 窄窗、页签、滚动/分栏和低位字段可用；状态反馈可见。
6. 提交非法批次保旧，继续合法修改；删除/换绑后旧弹层和旧请求不得写新对象。
7. 导出界面文档，再在同一进程预览并载入更新；业务草稿不随结构被提交或清空。
8. A/B 分别 Apply，公开按对象读回；正常关闭。
9. 新端点启动，用刚保存的界面文档重新装入并编辑；旧 endpoint-bound plan 拒绝，正常关闭。

rules 第二业务跑一条较短链，覆盖公共适配、两对象、自己的一套多定义文档、新字段/规则、持久化、重开精确读回和正常关闭。旧 SDK 消费者源码保留，只换本包 SDK 后做受影响的升级链；不把旧源码偷偷改后宣称零改动升级。

连续性若被 Sol 已知 runtime 问题阻断，保留原输入与精确事实，暂停依赖该问题的步骤并集中交接；独立资产/协议/开发入口继续。不能补点击、延时或重发救绿，也不能仅因完整测试被在途文件阻断就删测试宣布全过。

### 10.3 开发成本和运行成本各量各的

在既有 RESULT 用一小段记录：

- 新字段/规则实际改了哪些业务位置、哪些只是布局引用、是否仍有重复公共胶水。
- 运行中改变布局/两个组合/呈现的真实构建次数、重启次数；业务代码修改的构建另外计。
- 有界正常更新样本的候选接受耗时、既有 build/layout/prepare/submit 计数、同一真实 PID 的 CPU/RSS 与空闲是否继续工作。说明硬件、样本和测量边界。
- 静置与重复合法更新是否持续增长。若有新无界增长或明显长阻塞，定位本包引入的部分；Sol 范围内给精确交接，不新增性能引擎。

不能用几十毫秒的协议应答宣称首帧或输入到像素达标；不拿 wrapper PID 算应用 CPU，也不把 native=-1 当耗时。16/32ms 历史门不因本包改名通过。

### 10.4 一次正式冻结

复用 [exporter](../../runtime/cjgui/scripts/export_framework_preview.sh) 的 format 2 闭包锁，把本包公共源码、Python、必要示例、资源、用法和创建入口一起交付。不要散成 SDK + 五个历史 delta 才能用。

最终冻结前汇合已明确接收的 Sol 增量；没有新交接就保留 DS47 已接受运行时并列清身份。不能拿主树时间最新文件作为“已接受”依据。

一次同锁复导出核可重现，包外含空格路径创建/构建/使用本包公共示例，最终应用链使用该输入身份。同源重新编出的 native 归档与包内预置归档分开记，不要求两者字节必然相同。

README 第一屏给开始方式、公共指南和支持范围；开发者不应先读 RESULT 才知道如何使用。本包仍是 experimental 公共子集，不借 `additive_only` 声称任意旧私有工厂无条件兼容。

## 11. 长跑时怎样避免空转

阶段内部“能编译”“定向绿”“第一次窗口出现”只是进度，不是停工回报点。普通编译、路径、脚本、接线问题自行解决；新格式与 Python 解析现在都是 DS 写集，不再形成跨线等待。

默认顺序是 5→6→7→8→9→10；若本地代码证明某段已有可复用实现，就直接补其缺口与实际消费，不为顺序重写。可以在构建期间写独立文档/客户端，但同一 target 的 build/test 和桌面操作不得竞争。

每次验证先说清它要决定什么。出现多轮只改脚本/日志、核心能力没推进时，缩小到能区分问题的实验或改施工方法，不能把剩余 goal 轮数当必须跑满的配额。数据、身份、事务和资源正确性的必要断言不能放松。

真正需要集中交指导的情况：Sol 写集冲突、公共契约存在互斥选择、重大状态/FFI/生命周期风险仍不明、或依 AGENTS 已反复低收益失败。报告复现/假设/结果和推荐选择；只暂停相关依赖，不因此停止其余整包。没有新证据不轮询和重复报等待。

本包不顺带做递归/脚本引擎、完整 SVG/JPEG 管线、DatePicker/大批模式控件、全平台、全 VO/IME 或 GiB 矩阵。这些是保留的框架方向，不用本包完成冒充它们完成；Linux 继续封存。
