# 用仓颉写了个 GUI 框架，想让人和 AI 都能用

最近在做一个 GUI 框架，叫 CJGUI。用仓颉写，先做 macOS，走自绘路线。目前还是开发预览，拿出来聊聊思路和进展。

先放一段文档窗口的演示：

![窗口编辑、外部接口修改，再回到窗口继续编辑](https://raw.githubusercontent.com/aiulms/cjgui/main/docs/assets/demo/cjgui-shared-document-real-demo.gif)

这段录屏里，先在窗口中输入文字，再由外部程序通过公开接口追加一段内容，然后回到窗口继续输入。最后从接口读回来，能拿到接着编辑后的内容和版本。

外部这一步是脚本调用，展示的是给 AI 接入的操作接口，没有在视频里接模型推理。

我想做的使用方式大概就是这样：文档开着，人可以改，AI 也能读取和修改，人随时可以继续接手。换成规则编辑器也一样，自己在界面里调整几条，让 AI 帮忙批量处理一部分，再回到界面检查结果。

为此，应用需要告诉外部调用方：这里有哪些对象，可以读什么，可以执行什么操作。这样就能直接按对象和动作调用，不必每次都从截图里找按钮。

当然，给应用加 API 并不是什么新鲜想法。我想尝试的是，把这类接口需要的对象标识、授权、版本检查和变更读取做成框架里可复用的部分，写不同应用时能少重复一遍。

拿文档来说，窗口输入和外部修改最终都交给管理文档内容的同一个模块。外部程序读到了版本 13，提交修改时也要带上这个版本。如果期间人在窗口里又写了几个字，版本已经变了，这次请求就会被拒绝，调用方需要重新读取再决定怎么改。

这并不能自动解决所有编辑冲突，但至少不会拿旧内容直接盖掉人刚写的东西。

最近也看了 A2UI 和 json-render。它们让模型用结构化数据描述界面，再由客户端渲染成组件。我希望 CJGUI 也能承接这种用法：界面可以由开发者用仓颉写好，也可以由 AI 根据任务动态组合。例如，规则编辑器的主体由开发者设计，某次批量修改需要的确认面板交给 AI 生成，使用应用允许的组件和操作。

谁生成界面，和谁使用界面，可以分开考虑。开发者写好的界面可以让 AI 参与操作，AI 生成的界面也可以让人继续使用。两边修改的仍然是同一份应用内容，业务规则也照常生效。

所以 CJGUI 的主要工作还是 GUI 框架本身。仓颉负责组件、布局和交互逻辑，Metal 负责场景合成，macOS 的窗口和系统文字服务通过 AppKit 接入。自绘的方向参考了 GPUI，不过目前没有和它做过同条件性能对比。

文字排版和输入这部分会继续复用系统服务。要自己处理的，是输入之后怎样更新文档、刷新界面，以及刷新时怎样保住焦点、选区和滚动位置。这些细节做不好，编辑器很快就会变得难用。

开发中已经遇到过一个挺具体的问题：中文、emoji 后面继续输入英文，文档内容和辅助功能读取都是正确的，屏幕上的字却花了。后来查到，是把系统字体的 fallback 结果当成基础字体变化，又重新设置了整段字体，破坏了已有的字形回退。最后修的是字体更新的判断条件。

这类问题光看接口返回成功是发现不了的。文档确实改对了，画面还是可能错。所以现在除了测试内容和版本，也会用窗口样例检查实际显示和后续操作。

目前主要用两个应用来检验框架：一个共享文档窗口，一个规则集编辑器。前者用来跑文字、选区和外部范围修改；后者用来跑列表、详情表单、草稿和批量操作。另有独立的小应用验证导出的框架能不能正常使用。

组件组合、布局、滚动区、虚拟列表、菜单快捷键、图片和文字绘制已经有实现。性能上先处理能明确看到的重复工作，比如内容没变时少重建，稳定布局能复用就复用，列表只创建需要显示的行。现在还不足以给出一个能代表整个框架体验的性能数字。

它离日常放心使用还有距离。公共 API 还在调整，系统输入法和 VoiceOver 的完整验证、外部应用拖入文本、安装与公证这些也还没做完。当前主要试用环境是 macOS / Apple Silicon 和仓颉 1.1.3。

目前的窗口还是用仓颉编写的，用来验证组件和交互。AI 动态组合界面的接入尚未实现，后续可以通过 A2UI 一类的适配，把经过校验的界面描述转换成 CJGUI 组件，动作接到应用开放的业务接口。开发者也可以完全不接 AI，直接用它写普通桌面应用。

项目地址：[CJGUI](https://gitcode.com/aiulms/cjgui)。仓库里有演示、运行方法和当前进度。

第一次发出来，想找些做桌面应用或者对仓颉感兴趣的朋友看看。有合适的小工具场景，也欢迎拿来试试。比起继续往样例里加按钮，我更想知道它在别人的应用里会卡在哪里。
